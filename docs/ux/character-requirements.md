# キャラクターが弾く画面 要件定義（v1）

2026-11-23 版。`/` の画面（2026-11-24 に操作画面をなくし、この画面だけにした。前の `/character` は `/` へ移る）。体験の狙いと理由は [character-performer.md](character-performer.md)（UX 要件）にあり、この文書はそれを「作るもの」と「できたと言える基準」に落としたもの。

## 1. 目的

作業中ずっと流しておく即興ピアノに、**弾いてくれている子**を付ける。
「この子が、自分のために、いまここで弾いてくれている」と感じられて、安心して作業に戻れる。ときどき目をやると応えてくれていて、育った姿を人に見せたくなる。

## 2. 利用者

| | 利用者 | v1 |
|---|---|---|
| A | 作り手本人。家で作業・読書・考えごとをしながら、何時間も流しておく。目は作業に向いていて、見るのはときどきの一瞥。手はキーボードの上 | **中心** |
| B | A が共有したスクリーンショットや GitHub を見る人 | 画像の保存だけ（見る人向けの機能は作らない） |

## 3. 場面

1. **作業中（主）**：PC の別タブか、画面の隅の小さな窓。音はスピーカーかイヤホン。ときどき目をやり、気に入ったらキー 1 つで伝える
2. **夜、スマホで（副）**：縦の画面、片手、イヤホン。じっくり眺める
3. **見せたくなったとき**：いまの一場面を画像で残す
4. **止めているとき**：開いても演奏は止まっている。ピアノの前で待っている

## 4. 機能要件（v1）

状態の欄：**済** = 試作 v0 にある／**一部** = あるが要件に足りない／**未** = まだ無い。

### C1 開けばもう弾いている — 一部
- 開くとすぐ、ピアノの前に座って弾いている姿を出す。演奏はサーバーでいつも続いているので、途中から見せる
- 音は「▶ 聴く」の 1 タップで出す（ブラウザが音の自動再生を許さないため）。音が出ていなくても、絵は弾き続ける
- タブのタイトルに、いま弾いている曲を出す（「♪ 曲 12 ・ E♭ major — Amane」）— 済
- 読み込み中は、暗い部屋とピアノだけを先に出し、キャラは読み込めたら静かに現れる（「読み込み中」の文字や回る印は出さない）— 未

**受け入れ基準**：2 回目以降に開いたとき、2 秒以内に弾いている姿が出る（モデルはブラウザのキャッシュから読む。14MB のモデルで要測定）。▶ を押してから音が出るまで 1 タップ。

### C2 聞こえている音と動きが合う — 一部
- 鍵盤が沈む・手がその音域へ動く・指が押す、を**この端末で耳に届いている音**に合わせる（配信の遅れを補正する。評価と同じ「聞こえている時刻」）— 済
- 音が鳴る前に手がそこへ着いている（次の音に間に合うように動き始める）— 済
- 指の細かい動きは合わせきれないので、**手の位置と押す強さ**で見せる。指は「どの指が押したか」がそれらしく見えれば足りる — 済
- 鍵盤が沈むのは、どちらかの手が届くところだけ。手が次へ移ったあとも鳴っている長い音は、ペダルで響かせている体で鍵盤を戻す — 済
- 手は、音のまとまりが手の中に収まらなくなったら、その真ん中へ移る — 済
- 音を出していない（▶ を押していない）ときは、サーバーの時刻に合わせて動く — 済

**受け入れ基準**
- 音と鍵盤の沈みのずれが 0.1 秒以内（目安）— **済**（2026-11-23。`tools/measure_sync.py` で配信を録り、音の立ち上がりと音符の時刻を突き合わせた。5 回とも +35〜40ms で一定。MP3 の頭の無音のぶんなので、画面側で 40ms 引いて合わせた。スピーカー・イヤホンの遅れは含まない。Bluetooth のイヤホンは 0.1〜0.3 秒ほど遅れることがあり、そのときは基準を超える。未対応）
- 沈んでいる鍵盤は、その瞬間どちらかの手の幅の中にある — **済**（2026-11-23、2.5 分・約 600 打鍵を 33ms ごとに見た。鳴った直後の手との距離は中央値 2.6cm、8.5cm を超えたのは 1.5%、鳴ったのに沈まなかったのは 4.3%。直す前は、沈んでいる鍵盤の 11% が手から 8cm 以上離れていた）
- 指が鍵盤に埋まらない・反り返らない（静止画で正面・横から確かめる）— 済

### C3 演奏する人としての気配 — 一部
- 目線は手元の鍵盤。顔は少し伏せる程度（上を向かない）— 済
- まばたき、呼吸の小さな揺れ — 済
- テンポと強さに合わせた体の揺れ（速い・強いところで大きく、静かなところで小さく）— 一部
- 曲の始めに手を構える、曲の終わりに余韻を残して手を膝へ下ろす — 未
- 曲と曲のあいだに小さな仕草（息をつく・肩を回す・楽譜を見る）。何種類かから選び、同じものが続かない — 未

**受け入れ基準**：30 分見ていて、同じ仕草が 2 回続けて出ない。曲の終わりで手が鍵盤の上に止まったままにならない。

### C4 伝えたことへの反応 — 一部
- 「いい」：うれしそうな表情とうなずき — 済
- 「微妙」：少し考える表情。次のセクションで弾き方が変わる — 済（表情）
- 言葉の指示：軽くうなずく — 済
- 表情はすぐ消さず、**一瞥で分かるように数十秒かけて戻す**（作業中に伝えて、あとで目をやっても「伝わった」と分かる）— 未（いまは数秒で戻る）
- 反応は小さく。音・点滅・大きな動きは出さない — 済

**受け入れ基準**：キー 1 つで伝えてから 0.5 秒以内に表情が変わる。30 秒後に目をやっても、まだ反応の名残がある。

### C5 育っていく姿が見える — 一部
- 何回伝えたかを出す — 済
- 覚えた好みを、**この子の言葉で**出す（「あなたは、静かで余白の多い曲が好きみたいです」）。初期値から離れた好みの次元を 1〜2 個選んで文にする。16 個の数値は出さない — 未（いまは 5 つの目盛り）
- ときどき（曲の合間に、多くて 1 時間に 1 回）、変化を言う（「前より静かに弾くようになりました」）— 未
- できごと（評価・言葉・反応）を時刻つきで残す — 済（画面にいる間だけ）

**受け入れ基準**：評価を 10 回したあとで、覚えたことの文が初期状態と違っている。

### C6 一瞥で分かる・作業の手を離さない — 一部
- 幅 320px の窓でも、弾いている／止まっている／反応した、が分かる — 一部（2026-11-23。320px で崩れ・横スクロールが無いことを確かめた。見出しの文字を隠し、「▶ 聴く」を小さくして顔にかからないようにした。反応が一瞥で分かるかは C4 の表情の名残が要る）
- ほかの窓の上に小さく浮かべられる（ピクチャー・イン・ピクチャー）。浮かべた窓でもキー操作ができる — 未
- キー 1 つで伝える：`+` いい、`-` 微妙、`n` 次の曲、`Space` 聴く／止める、`f` 全画面 — 済

**受け入れ基準**：Chrome で、浮かべた小窓から `+` を押すと評価が付く。

### C7 見せる — 一部
- いまの一場面を画像（PNG）で保存。操作の部品は写さず、キャラとピアノだけ — 済（2026-11-23 に押して確かめた。ファイル名は端末の時刻）
- 全画面 — 済（2026-11-23 に押して確かめた。舞台だけが全画面になり、`f` でも出入りできる）
- 画面の枠・LIVE・演奏者名を含めた「配信の一枚絵」としての構図 — 済

**受け入れ基準**：保存した画像に、キャラの顔から手元の鍵盤までが収まっている。

### C8 操作 — 済
- 聴く／止める、音量、いい／微妙、次の曲。いまの曲・調・拍子・テンポ・和音の列（鳴っている和音が光る）・セクションの進み具合
- 言葉の指示（入力欄と、よく使う言葉の候補）。入力欄に曲の URL を貼ると、その曲を聴いて曲調を覚える（聴きに行くとうなずき、覚えたらうれしそうにする。2026-11-24）、演奏の一時停止・再開（`p`）、いまの曲を MIDI で残す（`s`）、残した曲の一覧とダウンロード — 2026-11-24 に操作画面から移した
- 好みの値を直接動かすスライダーは置かない（2026-11-24 決定。好みは評価と言葉で伝える。16 個の数値は裏側に置く）

## 5. 非機能要件

| | 要件 |
|---|---|
| 負荷 | 何時間開いても、PC が熱くならず、ファンが回らない程度。この PC は YOU で GPU を常に使っているので、それを邪魔しない。**基準：CPU は 1 コアの 20% 以下、GPU はこの画面の分で平均 15% 以下**（2026-11-23 の実測から置いた。下） |
| 負荷の実測 | 2026-11-23、この PC（RTX 5070）で画面のないブラウザ（Chromium headless・実 GPU）に開き、音も受けて 57 分。CPU は 1 コアの平均 14%（最大 15%）、GPU はこの画面の分で平均 10%（最大 38%）、1 コマの計算は 1.5〜3ms、描画は 1 秒 30 コマ。YOU と同時に動かして、YOU 側の GPU 使用に目立った邪魔はなかった。画面に実際に映す分（合成）は含まない。熱とファンは見ていない |
| 負荷を下げる仕組み | 画面が見えていない（別タブ・最小化）ときは描画を止め、音だけ続ける — 未。描画は低消費電力の GPU を選び、解像度は端末の 1.5 倍まで — 済。小窓のときはさらに解像度とコマ数を下げる — 未 |
| 長時間 | 8 時間開いたままでもメモリが増え続けない・止まらない。配信が切れたら自動でつなぎ直す。**未達の疑い**：57 分でブラウザ全体のメモリが 818→902MB、JS のメモリが 25→40MB と、少しずつ増えた。頭打ちになるかは未確認（8 時間で測る） |
| 音を邪魔しない | 点滅・大きな動き・通知音を出さない。動きを減らす設定（prefers-reduced-motion）では、雨・粒子・体の揺れを止める — 未 |
| ネット | three.js と three-vrm は同梱。外のサイトへつながなくても動く — 済 |
| 対応環境 | PC の Chrome（主）、Android の Chrome。iPhone の Safari は未確認 |
| 画面の幅・高さ | 320px 〜 PC の全画面。**ページは縦にも横にもスクロールさせない**（2026-11-24。画面の高さに収め、余った高さを舞台に使う。記録が多いときは古いものから切る）。右の列はチャット（YouTube のライブ配信の並び）。幅 900px 以下では、チャットを舞台の下に置く（YouTube のスマホ版の並び） — 済（1920×1080〜320×568 の 9 通りで確かめた） |
| プライバシー・公開 | 認証が無いので、信頼できるネットワークの中だけで使う。外へ何も送らない |
| 素材の権利 | キャラのモデルはリポジトリに入れない（`data/character.vrm` か `PIANO_VRM`）。試作の仮のキャラ（手元の VRM）は、公開ページ・画像・リポジトリに出さない。新しいキャラを AI で作るなら、そう明記する |

## 6. 制約

- ブラウザは、ユーザーの操作なしに音を出せない（C1 の 1 タップはこのため）
- 配信の音は数秒遅れる。動きは遅れを補正して合わせるので、遅れの分だけ「先の音符」をサーバーから受け取る（`/api/notes`）
- いまサーバーから受け取れるのは、音符（時刻・長さ・高さ・強さ・左右の手）と、セクションの区切り（始め・終わり・intro〜outro の別）。曲の終わりは outro の終わりから分かる。ペダルの情報は無い（v2 のペダルにはサーバー側の追加が要る）
- モデルは VRM 0.x と 1.0 のどちらも読む。向きの違い（0.x は後ろ向き）は読み込み時に吸収する — 済
- 絵柄は 3D 調になる。目指す 2D の一枚絵の雰囲気（暗い青・手元の光・雨・粒子・トゥーン調の陰影）は 3D で寄せる

## 7. v2 以降の候補（v1 ではしない）

- **2D の一枚絵＋差分**（本来目指す絵）。手の位置の差分をどう持つかは、v1 の手の動きの仕組みを流用できるか確かめてから
- **新しいキャラ**（世界観に合うピアノ弾き）。v1 は手元の仮のキャラで作る
- ペダルを踏む足（サーバーからペダルの情報を送る）
- 時間帯で部屋の明かりが変わる（朝・昼・夜）
- 短い動画（数十秒）の保存
- 公開の試聴ページ（GitHub Pages）にもキャラを出し、録音に合わせて動かす
- 曲間の仕草を増やす、時間帯で仕草を変える

## 8. 対象外

- ほかの人向けの配信（配信サービスへの出力、コメントへの反応）
- 口の動き・歌・しゃべる声
- MIDI キーボードで自分が弾いたのに合わせて動く
- 複数のキャラ、キャラの着せ替え

## 10. v1 で残っている作業（優先順）

1. ~~確かめる：音と動きのずれ（C2）、幅 320px、画像の保存と全画面、1 時間の負荷~~（2026-11-23 済）。メモリの増え方を 8 時間で測り、増え続けるなら原因を直す
